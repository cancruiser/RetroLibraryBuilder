What's changing in Retro Library Builder

A more approachable Guided experience, a storage-efficient unified ROM Library and expanding handheld knowledge — built on RLB's existing preservation-first foundation.

Important status distinction: The Raspberry Pi 3B+ Batocera, Recalbox, RetroPie and Lakka deployment tracks are physically accepted and frozen. Guided presentation changes, handheld firmware writing and broader device support are active Beta work and should not be read as equivalent acceptance claims.

Guided: a simpler route to a finished device

RLB is refining a visual, beginner-oriented step-by-step workflow: Home → Device → Protect → Choose → Games → Review → Build → Finished. Guided aims to make device selection, preservation, firmware choice, collection selection and safe writing understandable without requiring users to know partition names or firmware internals.

Advanced remains available for users who need granular inspection and control. Both experiences are intended to orchestrate the same established device, preservation, Library and deployment services; this is a UI/UX evolution, not a second implementation of the proven build engines.

One logical Library, not a copy of every discovered file

RLB consolidates identified ROM content across physical sources. Multiple identical physical ROMs do not automatically become multiple Library entries. Canonical titles, meaningful ROM variants and physical duplicates are separate concepts. Hash and catalog evidence support identification and review.

ROMs on persistent local drives, external drives and accessible network storage can remain in place as logical Library references. Needed new ROMs found on SD cards must first be preserved to durable PC storage. Originals are not renamed, moved or deleted. Other managed lanes include BIOS, artwork, saves and configurations, subject to supported workflows.

Build your collection

Selection work is expanding beyond a raw list of files. The design includes region preferences such as USA, World, Japan or All; revisions and variants; major platform categories; optional generations; and arcade-specific choices such as vertical or horizontal games. MAME/arcade selection needs to account for ROM-set dependencies and available DAT evidence rather than assuming every discovered arcade zip is independently playable.

Saved reusable collections, practical capacity fitting and clear inclusion/exclusion explanations are design goals under active development. They should not yet be interpreted as fully completed or accepted features.

Smarter hardware and firmware knowledge

RLB is moving toward chipset, board, panel, boot asset and DTB-based identity instead of relying on inconsistent handheld product names. This matters especially for R36S/R36 Max hardware families and clones that may have visually similar shells but different internals.

Firmware discovery and catalog work includes ArkOS-family releases and other available firmware projects, with an emphasis on release/version visibility and mappings from each firmware's supported systems to native destination directories. These mappings must be retained consistently across future builds instead of guessed on each deployment.

Handheld deployment: progress and limits

RLB has exercised firmware acquisition, multipart archive preparation and card-writing paths during R36 Max testing. A completed image write alone does not establish a bootable, accepted handheld build: one new firmware card failed to boot, while a previously working card continued to provide a known-good comparison.

Panel selection, boot layout and hardware evidence therefore remain active test areas. Preservation and user warnings must be handled independently from whether the target has reached full deployment confidence. RLB's proven Raspberry Pi deployment paths remain the accepted benchmark.

What happens next?

Current priorities include refining the visual Guided experience without changing tested engines, improving firmware/version and system routing accuracy, and validating handheld end-to-end deployments on real hardware. Public capability claims will continue to distinguish implemented code, in-progress Beta behaviour and physically accepted results.
