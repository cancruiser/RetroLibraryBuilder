Core concept

Preservation

RLB preservation is not just “copy the SD card.” Its goal is to establish verified protection for the content and evidence that make a device reproducible and understandable.

What “preserved” should mean

A preservation is meaningful only when RLB can account for the content it intended to protect. That means knowing whether content has an established verified representation in the reusable Library or whether a verified copy must remain associated with the individual preservation.

RLB therefore separates content discovery, analysis, representation, retention and verification rather than treating the existence of a destination file as sufficient evidence.

Library content vs retained content

▦

Library content

Verified reusable content maintained independently of a particular preserved device. When the correct representation is proven, it can stand for the source content without another unnecessary device-specific copy.

◆

Retained content

Verified content that remains associated with a particular preservation because an appropriate Library representation could not be established.

Why verification matters

Two files can have the same name and the same length while containing different bytes. RLB's preservation model therefore uses cryptographic content identity where equality matters instead of relying on path, existence or file length alone.

Preservation principle: Do not claim that source content is protected simply because something with a matching filename or size exists at the destination.

Canonical Library representations

A reusable Library representation does not always need to be byte-for-byte identical as a container file to the original source. For example, a canonical ZIP can validly represent content when its payload identity has been verified even though the ZIP container itself differs in length or metadata.

RLB's representation logic is intended to prove the content relationship rather than apply a weaker container-size shortcut.

Analyze vs Apply

Analyze
Determines what reconciliation work would be required and presents the preview. Analysis itself does not establish new content.
Apply
Performs the approved reconciliation work required to establish verified representations or retained protection.

Long-running operations and interruption

Large devices can contain many thousands of files, so preservation work may be long-running. RLB uses background execution and durable preservation evidence so the application can distinguish completed work from an operation that was interrupted or could not persist its terminal state.

Do not infer completion from the UI label alone. During Beta, rely on the actual preservation result and verification state when deciding whether an original device is safely protected.

Preservation terminology

Represented
RLB has established a verified representation of the source content in the appropriate destination context.
Retained
The content is kept with the specific preservation rather than represented by reusable Library content.
Verified
The required evidence has been checked rather than assumed from a weak signal such as filename or length.
Conflict / Review
RLB found a condition that should not be silently treated as established and requires a defined reconciliation outcome or review.
