IMPORTANT DISTINCTION

RLB system support is not emulator support.

Retro Library Builder is separate from emulation. It does not choose emulators, benchmark cores or claim that a game runs correctly. System coverage describes what RLB knows how to identify, preserve, organize and route.

Identify

Recognize platform identity using registry, path, format, catalog and other evidence.

Preserve

Account for source content without modifying the user's originals.

Organize

Maintain reusable Library representations and system-specific structure.

Route

Place selected content into the native locations defined by a supported firmware/frontend profile.

BREADTH OF THE REGISTRY

Consoles, handhelds, computers, arcade and engines.

The registry is intentionally broader than a short list of popular cartridge consoles. Examples already represented in RLB include:

CATALOG & IDENTITY SOURCES

Multiple sources contribute different kinds of evidence.

The system registry and game catalog are not one monolithic database. RLB records the provider expected for each platform and reconciles catalog evidence from multiple ecosystems.

No-Intro

Major cartridge and single-file system identity/catalog coverage.

Redump

Disc-oriented catalog coverage for systems such as PlayStation, Saturn, Dreamcast, GameCube and others.

TOSEC

Broad computer and preservation-oriented catalog coverage.

MAME / FBNeo / community sources

Arcade, software-list and specialist-platform knowledge where those sources are a better fit.

COVERAGE IS MULTI-DIMENSIONAL

“Supported” is not one yes/no flag.

A platform can exist in the System Registry even when its current catalog coverage, hash depth, file-format routing or deployment profile is still incomplete. RLB keeps those states separate rather than pretending they are the same.

System Registry

Does RLB have a canonical platform entry, folder model and expected source/structure knowledge?

Catalog Coverage

Does RLB currently have title, alias and hash data for that platform?

Deployment Profile

Does a selected firmware/frontend define where that platform's content belongs on the target?

Physical deployment validation is separate again. It proves RLB's build workflow for a hardware/firmware combination; it does not test or certify emulation quality.
