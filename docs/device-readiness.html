Deployment safety

Knowing the device is not the same as being ready to deploy.

Device Readiness evaluates canonical identity, deployable targets, firmware evidence, confidence and blocking risks before RLB allows knowledge to become a deployment decision.

DEVICE READINESS — ACTUAL RLB INTERFACE
Safety gate: Device Readiness is allowed to say “not enough evidence.” A device can be recognized with reasonable confidence and still have zero safe deployment targets.

1. What Device Readiness is for

Device Readiness is the knowledge-side safety gate between device identification and Deployment.

It inspects the canonical device identity together with runtime knowledge about firmware, panels, DTBs, storage, recovery and other required evidence, then decides whether any deployment target can be considered safe.

2. Search the canonical device catalog

The workspace can search canonical devices, aliases, providers, DTBs and panels. The left-hand device list shows the matching canonical devices and gives each one a compact readiness summary.

4. The verdict is more important than the percentage

The Deployment Readiness panel gives an explicit verdict. In this example:

STOP
Not safe to deployBlocking evidence is missing. RLB should not convert the current device knowledge into a deployable target yet.

A 77% knowledge-confidence score therefore does not mean “77% safe.” Deployment safety depends on whether required evidence is present, not just on an average score.

5. Overall Readiness combines several evidence areas

The selected device can have different levels of evidence completeness across several categories.

86%HardwareSubstantial hardware evidence is already available.
0%PanelThe display panel remains unknown in the shown example.
70%FirmwareFirmware knowledge exists but cannot be considered safe without the missing panel evidence.
25%StorageBoot/storage-layout knowledge remains incomplete.
0%RecoveryRecovery evidence/procedure is incomplete.
100%Clone / FingerprintStrong clone/fingerprint evidence is already satisfied.

6. Blocking Risks explain why deployment is stopped

Device Readiness does not only show a failed verdict; it explains the specific evidence that prevents deployment.

!
Panel evidence is missingFirmware cannot be considered safe while the panel remains unknown. A wrong panel/DTB relationship can make otherwise plausible firmware unsuitable for the actual hardware.

The shown screen also warns that recovery is incomplete. These risks remain visible instead of being averaged away by stronger evidence in other categories.

7. Satisfied Evidence shows what RLB already trusts

Readiness also lists the evidence that has already been satisfied. In the R36 Max example this includes:

✓Clone fingerprint
✓Display / resolution evidence
✓Firmware recommendation
✓GPU evidence
✓SoC evidence

This is useful because a STOP verdict does not mean RLB knows nothing. It means the remaining missing evidence is important enough to block deployment.

8. Improve Confidence By tells you what evidence is still needed

The workspace provides concrete guidance for improving the readiness result rather than leaving the user with an unexplained failure.

1Collect boot/storage layoutEstablish how the device expects its storage and boot content to be structured.
2Establish firmware panel supportProve that the recommended firmware supports the actual display panel.
3Match DTB panel IDConnect the device's DTB/panel evidence to a known compatible hardware relationship.
4Add preservation / recovery evidenceEnsure a recovery path exists before treating deployment as safe.

9. Zero targets is a valid result

The example device shows 0 deployable targets. That is not a UI failure. It means the Knowledge Engine has not yet validated a deployment variant that satisfies the current safety policy.

KNOWN DEVICECanonical identity existsRLB knows which device entry is being evaluated.
≠
SAFE TARGETDeployable variant validatedEnough firmware, panel, storage and recovery evidence must exist before a target becomes deployable.

10. Recommended firmware is not automatic permission to deploy

The screen can show a recommended firmware family while still blocking deployment. In the example, the firmware recommendation is Linux, but panel evidence is insufficient to call that recommendation safe.

This distinction prevents a recommendation from being mistaken for a validated deployment recipe.

11. Knowledge decides safety; Deployment executes validated targets

The policy statement in the workspace is explicit:

KNOWLEDGE ENGINEDecides deployment safetyEvaluates canonical identity, evidence completeness, confidence and blocking risks.
→
VALIDATED TARGETOnly safe variants passA deployable target exists only after the required evidence satisfies policy.
→
DEPLOYMENT ARCHITECTExecutes validated targetsDeployment does not invent its own compatibility decision.

12. Reload Runtime Knowledge refreshes the decision layer

The Reload Runtime Knowledge action reloads the knowledge used by Device Readiness. This is useful after the managed knowledge repository has changed and the readiness evaluation needs to consume the updated evidence.

Device Readiness principles

✓Recognized device does not automatically mean deployable device
✓Blocking evidence must stay visible even when other confidence is high
✓Zero deployable targets is preferable to an unsafe guess
✓Recommended firmware and validated deployment target are different states
✓Deployment should execute only targets already validated by the knowledge policy
