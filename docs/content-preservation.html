Ecosystem preservation

RLB preserves more than games.

A retro-gaming setup is made from games, BIOS, media, saves, configuration, playlists, firmware assets and device-specific files. RLB treats those as parts of one ecosystem instead of disposable extras.

Preservation first: original content remains the authority. RLB is designed to account for source content before destructive media work is allowed.

Content lanes RLB understands

Games

ROMs, optical-disc images, playlists, archives and relationship groups.

BIOS & firmware support

BIOS files, boot ROMs, Kickstarts, IPLs and other system-support assets.

Media

Artwork and other frontend-facing assets associated with systems and games.

Saves & states

Battery-backed saves, save states and other user-progress data.

Configuration

Frontend, firmware and user configuration that belongs to the preserved environment.

Device-specific files

Boot, DTB, panel and other hardware-specific evidence that may be required to recreate a working device.

Relationships matter

RLB does not assume every file is independent. CUE/BIN sets, GDI groups, M3U multi-disc sets and computer-game folders can represent one playable release or package. Relationship detection occurs before content is reduced to individual Library items so required members are not separated accidentally.

Represented versus retained

When RLB can safely represent content in the managed Library, it records that representation. Files that are important but cannot yet be represented safely can be retained separately instead of discarded. Source accounting and preservation are therefore separate from canonical game identification.

Preservation is not the same as copying

A successful copy proves that bytes were written somewhere. Preservation asks a stronger question: was the original ecosystem accounted for, and is there enough verified information to recreate it later? RLB's workflow is built around that distinction.
