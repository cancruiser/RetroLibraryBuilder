Recovery workflow

Resume the preservation. Do not start over blindly.

When RLB has durable preservation state from an interrupted run, Resume Protection is the path back into that work. RLB revalidates the source and destination before reusing them and continues from persisted preservation state instead of assuming the previous run completed.

RESUME PROTECTION — ACTUAL RLB INTERFACE
Resume is not proof of success. The presence of a Resume action means RLB has persisted work it can attempt to continue. It does not mean the earlier preservation completed or that the device is already safe to erase or repurpose.

1. When should you use Resume Protection?

Use Resume when a preservation was interrupted or paused and Device Inspector exposes a Resume Protection action for that persisted preservation state.

Typical interruptions can include closing RLB, losing access to a removable destination, disconnecting a source, or otherwise ending a long-running preservation before its required work and verification finished.

2. Before clicking Resume, restore the same working context

Resume is safest when the same physical source and preservation destination used by the interrupted run are available again.

✓
Reconnect the original sourceIf the interrupted preservation depended on the source device, reconnect that same media rather than substituting a different card or image.
✓
Reconnect the preservation destinationUse the destination associated with the persisted preservation rather than pointing Resume at an unrelated location.
✓
Leave completed preservation data intactDo not manually delete or reorganize partial preservation content before RLB has had a chance to revalidate it.
✓
Keep the original media unchangedDo not erase, repurpose or modify the source simply because some preservation work already completed.

3. Open Device Inspector and look for the persisted state

Return to Device Inspector. When RLB recognizes a resumable preservation, the Actions pane can expose Resume Protection even though normal protection stages are not currently available.

4. Resume begins with revalidation

RLB should not blindly trust that a removable source or destination is still the same device simply because it appears at the same path or drive letter.

RESUMEContinue persisted workOnly after the required context is re-established should the interrupted preservation continue.
Why this matters: removable storage can disappear, reconnect under a different path, or be replaced by another device. Resume must bind back to the intended preservation context rather than assume “same location” means “same content.”

5. Resume should reuse established work

The purpose of durable preservation state is to distinguish work that was already established from work that still needs to be completed.

Resume is therefore not intended as a blind full restart. Work that RLB can validate as already complete can be reused, while incomplete or unverified areas remain work to do.

ALREADY ESTABLISHEDReuse validated progressCompleted durable work should not be discarded merely because a later part of the run was interrupted.
+
STILL REQUIREDContinue incomplete workProtection and verification that were not established must still complete before the preservation can be considered successful.

6. Long-running resumed work remains a background operation

Preservation can involve many thousands of files and may take hours. After Resume is accepted and its prerequisites are revalidated, the work should continue through RLB's long-running/background execution path.

Use the application's background-task/status views to follow actual progress rather than assuming the operation finished because you navigated away from Device Inspector.

7. If the run is interrupted again, do not clean up manually

If another interruption occurs, preserve the source and destination in place. RLB's persisted preservation state is what allows completed work to be distinguished from unfinished work on the next attempt.

✓
Leave durable state intactReconnect the required devices and let RLB reassess what can be reused.
×
Do not “fix” the preservation folder by handDeleting partial results can remove the very work Resume was designed to reuse or verify.

8. A resumed run still has to reach a verified terminal result

Resume changes how RLB continues the work; it does not lower the standard for completion.

Before treating the original device as preserved, confirm the actual persisted preservation/verification state. The same completion rules apply whether the work finished in one uninterrupted run or several resumed runs.

✓Required content accounted for
✓System / recovery protection established where required
✓User-content protection established where required
✓Verification completed
✓No interrupted or unresolved state is being mistaken for success

9. When Resume is not the right assumption

Do not treat the presence of a historical report, an old folder, or a familiar drive letter as enough reason to force a resume. The Resume action is meaningful when RLB has the persisted preservation context needed to offer it.

If the source or destination cannot be revalidated, the safe outcome is to stop and resolve that mismatch rather than continue against uncertain media.

Do not bypass a failed revalidation. A Resume that refuses to continue is protecting the preservation from being attached to the wrong source or destination.

10. Resume Protection vs Run Essential Protection

RESUMEContinue an existing preservationUses persisted preservation state, revalidates its context and attempts to continue incomplete work.
NEWRun Essential ProtectionStarts the protection operation for a currently analyzed device when no interrupted preservation is being resumed.

When RLB presents a valid Resume path, prefer understanding and continuing that persisted work rather than starting an unrelated new preservation simply because the previous run was interrupted.
