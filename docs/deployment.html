DEPLOYMENT INTENT

Rebuild with firmware

Install the selected compatible firmware on blank/replacement media and include only the systems and games explicitly selected for the build. Raspberry Pi builds expose First Boot Setup before the card is written.

Synchronize content

Keep the firmware already running on the target and add or update selected games, media, BIOS, saves, settings and supported user files through the firmware's network deployment path.

PLAN & PREVIEW
▦

Select systems and games

Choose a collection policy, one or more systems, complete systems or individual games. Optional media remains an explicit build choice.

◫

Complete ecosystem lanes

Plans can include ROMs, BIOS, artwork/media, saves, configuration and user data where the source/target profile supports those lanes.

◇

No-write preview

RLB can review deployment details and save a no-write manifest before destructive SD creation or approved network copying begins.

FIRST BOOT SETUP

Provision supported Raspberry Pi firmware before first boot

First Boot Setup is part of the accepted deployment workflow rather than a separate manual checklist.

Network

Configure supported Wi-Fi/network settings, including scanning nearby Wi-Fi from the Windows PC when applicable.

Hostname & shares

Apply firmware-supported hostname/network-share settings and preserve the RLB deployment identity needed for continuation.

Controller continuity

RetroPie can capture a configured controller profile from a running device and restore it during a later build so setup can be skipped when the profile is valid.

Retry without rewrite

If firmware writing verifies but First Boot Setup/identity needs attention, RLB can retry provisioning without rewriting the verified firmware image.

EXECUTION

The accepted safety sequence

The exact implementation varies by firmware, but the execution stages remain visible and ordered.

Choose a validated device and firmware targetKnowledge/readiness evidence is resolved before a writable target becomes actionable.
Acquire and verify firmwareRLB checks its firmware resources and the authoritative recipe before preparing the image.
Confirm the physical targetSD creation performs final target/capacity/safety checks and shows destructive confirmation before erasing media.
Write and verify the SD imageFirmware preparation and verification are separate from later content deployment.
Complete First Boot Setup and connectRLB waits for the firmware's real network service rather than substituting a generic Windows partition for Pi content.
Deploy approved Library contentSelected lanes are routed into firmware-native locations, including supported BIOS/media/user-data destinations.
Cryptographically verify deployed contentVerification compares destination content to the authoritative managed Library source.
Finalize the frontendApply firmware-specific metadata/settings and refresh/restart EmulationStation or RetroArch as required.
CONTINUATION & RECOVERY

Running-device continuation

For content-only work, RLB can discover a supported running Raspberry Pi firmware network share and continue deployment without rewriting the physical SD card.

Durable verified checkpoints

Completed copy/verification proof can survive restart. Accepted retry paths restore the checkpoint so ROM/BIOS content is not recopied or re-hashed just to finish frontend work.

Targeted repair/finalization

Recalbox artwork repair and Lakka/EmulationStation finalization can be retried independently when content deployment is already complete.
