Content recognition reference

ROM, disk, archive and playlist formats RLB understands.

RLB uses file format as one piece of evidence when identifying content. Unique extensions can strongly identify a platform; shared formats such as BIN, ISO, CHD, ROM and ZIP require system, folder, source or catalog context.

HOW FORMAT RECOGNITION WORKS

Extension + context, not extension alone.

Many retro platforms reuse the same container or disk-image formats. RLB therefore combines extension evidence with platform context rather than assigning every .bin, .iso or .zip file to one system.

1

Format

The filename extension provides an initial content clue.

2

Path / source

Folder names, source layout and known frontend structure help resolve shared formats.

3

Catalog evidence

Title, alias and hash evidence can strengthen or correct classification.

4

Review when ambiguous

RLB can keep uncertainty visible instead of silently inventing a platform match.

Important: Format support describes RLB content recognition and handling. It does not describe emulator compatibility, performance or game playability.

OPTICAL DISC & LARGE-MEDIA FORMATS

Disc images are frequently shared across systems.

PlayStation, Sega CD, Saturn, Dreamcast, PC Engine CD and other disc platforms can use overlapping image formats. RLB treats the surrounding system context as part of the identity evidence.

Shared disc formats

.cue .bin .iso .chd .img .ccd .mdf .toc

These require contextual classification rather than a one-extension/one-system rule.

Dreamcast

.gdi .cdi plus shared disc formats such as .chd, .cue and .iso.

PlayStation family

PlayStation: .pbp .ecm plus shared disc formats.
PSP: .cso plus .iso/.chd where appropriate.

Nintendo disc systems

GameCube: .gcm
Wii: .wbfs .wad
Wii U: .wux .wud .rpx

Multi-disc playlists

.m3u

Used where a platform/source represents a title as a set of related disc images rather than a single file.

Disc-oriented catalog evidence

RLB can combine file/layout evidence with catalog sources such as Redump rather than relying on image extension alone.

CONTENT BEYOND GAMES

RLB also manages BIOS, media, saves, configuration and device data.

Those content lanes do not have one universal extension list. Valid BIOS, save, configuration and media files depend on the platform, firmware and frontend being inspected or built.

WHAT “SUPPORTED” MEANS HERE

Recognition is not conversion and not emulation.

Recognized

RLB has a classification or contextual handling path for the format.

Contextual

The format is shared and needs path, system, catalog or source-layout evidence before RLB should classify it.

Target-dependent

Deployment routing is determined by the selected firmware/frontend profile. RLB respects the target's native structure instead of inventing an emulator layout.

RLB never needs to test emulation to support a content format. Its responsibility is identifying, preserving, organizing, verifying and routing the content correctly.
