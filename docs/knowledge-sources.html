Knowledge provenance

RLB should know where its knowledge came from.

Knowledge Sources shows the projects, communities and internal catalogs that contribute to RLB's managed knowledge repository, what each source is used for, and whether that source is currently enabled or refresh-capable.

KNOWLEDGE SOURCES — ACTUAL RLB INTERFACE
Credit the source: RLB is designed to bring together trusted knowledge rather than erase its provenance. Community projects remain identified and credited as the original source of the knowledge they contribute.

1. What Knowledge Sources is for

Knowledge Explorer answers “What does RLB know?” Knowledge Sources answers “Where did that knowledge come from?”

This workspace lists the providers that feed device, firmware, hardware, compatibility and related knowledge into the managed RLB repository.

2. The source summary shows repository status

The summary cards across the top separate four useful source states.

REGISTEREDRegistered SourcesEvery internal or community provider currently known to the source registry.
ENABLEDEnabledSources currently available for RLB to use.
SYNCSync CapableProviders that support a refresh/synchronization workflow rather than only static reference use.
COMMUNITYCommunity SourcesExternal projects and communities credited as knowledge providers.

The exact counts can change as sources are added, disabled or gain refresh support. The important part is that these are distinct states rather than one undifferentiated list.

4. Community sources remain first-class knowledge providers

The Device Knowledge section shows registered community and public-reference providers that contribute to RLB's understanding of devices and hardware.

Visible examples in the current Beta include AeolusUX R36S-DTB, approved console-history sources, a community handheld spreadsheet and Handhelds Wiki.

6. Enabled does not mean “equally authoritative”

An enabled source is available to RLB. That does not mean every claim from every source automatically becomes a canonical fact.

Different sources contribute different kinds of evidence, and RLB's canonical layer is responsible for reconciling aliases, contradictions, classifications and device relationships.

SOURCEContributed evidenceA project supplies device, hardware, firmware or historical information.

7. Sync-capable sources can be refreshed

The Sync Capable status identifies providers designed for refresh. This lets RLB distinguish refreshable sources from references that may require manual curation or a different ingestion path.

Refresh capability is a property of the source integration, not a guarantee that upstream data is complete or error-free.

8. Visit Project preserves attribution

Community-source cards provide a Visit Project action so the original project remains visible to the user.

This matters for two reasons: the source receives credit, and users can inspect the upstream project for context, documentation or updates that RLB should not pretend to own.

RLB is an integrator, not the origin of every fact. The project benefits from preservation projects, firmware developers, hardware communities and open-source contributors whose work should remain recognizable.

9. Provenance makes conflicts easier to reason about

When two sources disagree, source identity provides the context needed to investigate the discrepancy. Without provenance, RLB would only know that two values differ; with provenance, it can preserve which project supplied each piece of evidence.

1Keep the providerKnow which source contributed the evidence.
2Keep the evidence typeKnow whether it was a DTB, hardware specification, alias, firmware claim or historical reference.
3Resolve canonicallyUse RLB's managed knowledge layer to normalize without erasing provenance.
4Stay revisableNew or better evidence can improve the canonical result later.

11. The same knowledge ultimately supports Device Inspector

The long-term value of the source system is not simply building a large catalog. Managed knowledge gives Device Inspector more trusted relationships against which it can compare evidence from a real device.

A known DTB fingerprint, firmware relationship, board profile or device alias becomes useful when it helps RLB make a more accurate identification or compatibility decision.
